### C4 TRUTH
- **Tags.** Every ₹, %, count and probability in a report carries one; report numbers come from files in `results/` (cite the path); every owner-facing ₹ says PRE-TAX. - **Kill / pass asymmetry.** "Impossible" (an arithmetic kill) may rest only on SOURCE, REAL, OWNER inputs. To PASS anything, set every modelled or estimated input to its stress value. To KILL, set each modelled input to its most favorable defensible value: slippage ₹0, spread = the 10th percentile of ≥ 100 measured snapshots (with fewer, spread = 0 on the kill side), charges as sourced. So neither rests on a guess, and one lucky quote never kills an idea.
- MODEL premiums (no option quotes in the data) are always stressed and cap the verdict at PAPER_READY(MODELLED).
- **Units.** Every `_RS` value is rupees for the WHOLE structure at 1 lot (LOT units per leg). Spread and slippage are option points per unit per leg; rupees = points × LOT × legs × 2 sides. A premium is per unit; its rupee cost is premium × LOT.

- No look-ahead: signals use only data up to the closed candle; entry next bar.
- **What is REAL.** Probe snapshots (2b): premiums and OI always, bid / ask spreads only if the market was open. DATA-R: quotes, spreads, slippage at decision time. DATA-P: what the bot saw, decided and logged; its fills are modelled. "Forward" means "after FREEZE" and is never a tag. A mean from fewer than 30 trades is REAL but UNDERPOWERED.

### STATISTICS CONTRACT (the stricter of this and `gates.toml` wins; never weaken)
ST1 **Trial.** One trial = one distinct parameter vector of one idea evaluated on DESIGN data (controls included) = exactly one line in `trials.jsonl`: `{id, cycle, idea, params, design_net_stressed, p_screen, source}`. `k` = the number of lines. NOT trials: the matrix build and market facts of 3a and the arithmetic prefilter of 3b (no rule is evaluated; prefilter kills go to `results/prefilter.md`); the ±20% perturbation points of ST5 (one family per finalist, logged in `perturb.jsonl`); the stress and delay runs of ST7. ST3 **Null test (matched null, N6).** Random entries with the candidate's own entry window, trades per day, side mix, structure rule, RISK SHELL and exits: only its timing signal is removed. Screening: 1,000 runs, raw p ≤ 0.05, used only to drop candidates, never to pass one. Finalist: N = max(10,000, 400 × k) runs, p = (1 + #null ≥ observed) / (N + 1). The finalist passes only if Holm-Bonferroni over all k trials rejects it: sort the p-values p(1) ≤ p(2) ≤ …, reject p(i) while p(i) ≤ 0.05 / (k − i + 1), stop at the first failure. Every non-finalist counts in k but enters with p = 1 (never rejected; its coarse screening p can never block a finalist's step-down), so m finalists face 0.05 / k, 0.05 / (k − 1), …, 0.05 / (k − m + 1). Why N: the smallest possible p is 1 / (N + 1) and Holm needs it ≤ 0.05 / k, so N ≥ 20k − 1 [CODE: arithmetic]; for k = 30 / 42 / 54 / 66: N ≥ 599 / 839 / 1,079 / 1,319 and the contract N = 12,000 / 16,800 / 21,600 / 26,400. ## BOT · the bot spec + Phase 4 (build), Phase 5 (replay + docs), Phase 6 (review + PR)

Extend the M0 code (C10); do not rewrite it; a piece named below that is missing is built minimal. Modes: PAPER (default: live or replay feed, fills by PaperBroker, B12) · LIVE (locked). Never wait for DATA-R or DATA-P. The broker has NO reduce-only flag (Phase 2): a sell above the open long opens a short, so every exit rule below exists to make that impossible.

### SPEC
B1 **Strategy**: a pure function of data up to time t (`bot/strategy/`), behind `bot/contracts.py`. The same module runs in the engine of record, replay, paper and live. **Determinism (N8):** one injectable Clock (`bot/clock.py`) with `now_ist()` for time stamps and `mono()` for every interval (timers, quote age, heartbeat) and `SEED`; no `datetime.now()`, `time.time()`, `time.monotonic()` or unseeded `random` anywhere else under `bot/` (a grep test); replaying the same input twice gives byte-identical journals (a test).
B2 **Gateway** (the single chokepoint; the only module allowed to call the broker order API; entry points `submit`, `reduce_only`, `tighten_stop`; an AST scan test for Python and a grep test for Go enforce it). Timing and ladder numbers live in `config/gateway.toml` (pinned, K0); the defaults below are ASSUMPTION, tighten-only, and a schema test enforces each bound.
   - *Entry checks (`submit` only; every one):* symbol whitelist (BANKNIFTY index options only, R1; `tests/test_scope_banknifty.py`, which also rejects a credit-spread intent); structure = one long option or one debit spread whose Leg 1 is the long leg (R2); quantity = 1 lot per leg (LOT from the instrument master); `state/hard_kill.flag` absent; `worst` = by-construction max loss ≤ `MAX_TRADE_LOSS_RS` (premium × LOT for a single option, net debit × LOT for a debit spread, each plus stressed round-trip charges; computed BEFORE Leg 1 is sent and AGAIN from Leg 1's actual fill before Leg 2); **remaining budget:** realized loss today + `worst` ≤ the daily lock, and the same for the week, the month and `MAX_TOTAL_LOSS_RS` (equity now − `worst` ≥ `EQUITY_FLOOR_RS`); the shell's day rules (≤ 2 entries per day; the day is over after one full loss = a net loss ≥ 0.5 × `MAX_TRADE_LOSS_RS`); cool-off `COOLOFF_MIN` (written in 3e, ≥ 15); limit within `PRICE_BAND_PCT = 2` % of the fresh quote; idempotency key; balance gate (RULES K3) and, in LIVE for a spread, the broker margin call for both legs × 1.15 ≤ usable funds (else `NO_TRADE MARGIN_INSUFFICIENT`, before Leg 1); no entry after `ENTRY_CUTOFF_IST = FORCE_FLAT_IST − max(20 min, the strategy's time-stop)` (an expiry day counts from `FORCE_FLAT_EXPIRY_IST`), on a special session, on stale data (the underlying AND the traded contract each received ≤ `STALE_ENTRY_S = 3` s ago by `Clock.mono()`, and the exchange stamp within −1 s … +3 s of `now_ist()`, else `NO_TRADE STALE_FEED`), while reconcile is not CLEAN, while `state/watchdog.beat` is older than 10 s (`LIVE_BLOCKED WATCHDOG`), with < 50 MB free on `state/`, or in a FENCED process. When Phase 2 says `X-Algo-Name` applies, every order carries it from config `ALGO_NAME` (empty → LIVE_BLOCKED).
   - *Exit checks (`reduce_only`, `tighten_stop`, cancel; ONLY these):* symbol whitelist; the order closes or reduces an open leg (opposite side; quantity ≤ the broker's open quantity of that leg minus same-side working exit orders, never above 1 lot); the idempotency key; the exit rate budget. An exit is NEVER refused by HARD KILL, a lock, cool-off, the balance gate, day rules, the cut-off, stale data, an unclean reconcile, LIVE_BLOCKED (IP, CLOCK, WATCHDOG, DISK), `X-Algo-Name`, the 1-lot rule or the entry price band. A refused exit is an alarm (`FLATTEN_REFUSED <reason>`, B10) and the next rung goes at once.
   - *Rate budget:* order calls (place, modify, cancel) per process: entries ≤ 2 per second; exits a reserved ≤ 6 per second that entries cannot use (combined ≤ 8, under the broker limit of Phase 2); reads (order book, order details, positions, quotes) a separate budget; ≥ 250 ms between two modifies of one order; HTTP 429 → wait `Retry-After`, else 1, 2, 4, 8 s, journal `RATE_LIMITED`; an exit is never queued behind an entry.
   - *Write-ahead and idempotency:* every broker request first gets an Intent Log record `{intent_id, leg, action, attempt, epoch, key, state=PENDING_SEND}`, written and fsynced; `key` = the first 16 hex of sha256(`intent_id|leg|action|attempt|epoch`) (shorter if Phase 2's tag limit says so; the log keeps the full hash), sent as the order `tag`; a retry of the same attempt reuses it. Every HTTP call has `T_HTTP = 3` s. Timeout, 5xx or a lost connection → that leg is `UNKNOWN`: no order of any kind for it; poll the order book by `tag` every 1 s up to 10 s: found → adopt its id and status; absent at two polls 5 s apart → `NOT_SENT`, and only then retry with `attempt + 1`. A REJECT closes the key. At start every `PENDING_SEND` / `UNKNOWN` record is resolved this way before reconcile ends.
   - *Structure state machine* (one intent, `intent_id`; the full table is `docs/STATE_MACHINE.md`, one row per (state, event) pair; an unlisted pair journals `UNHANDLED` and goes to EXITING; every transition is written to the Intent Log before the action it starts):
     · BOOT_RECONCILE → FLAT (broker flat, log clean) or ORPHAN (the broker holds a position or order the log does not) → EXITING.
     · FLAT → L1_SENT: Leg 1 = the long leg, limit = best ask + ≤ 1 tick, within the cap, one price, no re-pricing. L1_SENT → L1_FILLED only when the order book shows Leg 1 `complete` with filled qty = LOT. Not complete within `T_L1 = 3` s → cancel, wait for a terminal status: filled 0 → FLAT; 0 < q < LOT → flatten q, NO_TRADE. Reject → FLAT. Timeout / 5xx → L1_UNKNOWN (write-ahead rule).
     · Single option: L1_FILLED → SL_PENDING (broker-side SL-limit for the position, with protection per Phase 2) → OPEN1 only when the order book shows that stop `trigger pending` or `open` for the full quantity (poll every 0.5 s, up to 2 s); not seen, or rejected (also later) → flatten at once. While OPEN1, every 5 s: working stop qty ≠ open qty → re-place the stop or flatten.
     · Debit spread: L1_FILLED → L2_SENT within `T_L2_DECIDE = 2` s on a fresh quote: the max loss recomputed with Leg 1's actual fill and Leg 2's limit must stay ≤ the cap; Leg 2 limit = the bid or one tick under it, never beyond that bound; Leg 2 quantity = Leg 1's filled quantity; otherwise flatten Leg 1. L2_SENT → OPEN2 when Leg 2 is `complete` with qty = LOT. Unfilled at `T_L2 = 2` s, rejected, or Leg 1's mark-to-bid loss reaches 0.5 × `MAX_TRADE_LOSS_RS` first → L2_CANCELLING: send cancel and poll until Leg 2 is terminal (a cancel reply is not proof); q2 = Leg 2's filled qty: q2 > 0 → buy back q2 first, then sell Leg 1; q2 = 0 → sell Leg 1. Not terminal in 2 s → L2_UNKNOWN: do NOT sell Leg 1; retry the cancel every 1 s; at 10 s flatten both legs from broker truth, short first, and alarm. Leg 2 confirmed dead with q2 = 0 and Leg 1 not sold within 2 s → a broker-side SL-limit on Leg 1 (no short exists, so it cannot leave a naked short).
     · OPEN1 / OPEN2 → EXITING on a stop fill, target, time-stop, scratch, chase, FORCE_FLAT, feed freeze, token, HARD KILL, the daily mark-to-market lock or a leg that closed alone. A debit spread exits EXIT_SHORT (buy back the short until the broker shows it `complete`, short qty 0) → EXIT_LONG (sell the long). **Hard invariant:** no sell, stop or reduce order on the long leg while the short leg's open qty > 0 (a TRIGGERED stop is not a filled one). A leg that closes alone → the other leg is flattened at once (a lone short first, on the buy side of EXIT_LADDER).
     · EXITING → FLAT only when the broker shows net 0 on every leg AND no working order on the intent's contracts. EXIT_LADDER exhausted → EXIT_STUCK. HARD KILL → LOCKED. A stale epoch → FENCED.
   - *Stops.* Single option: the broker-side SL-limit of SL_PENDING. Debit spread: NO broker-side stop on either leg (its loss is bounded by the net debit while both legs are held; a stop on the short leg fires on winners and its trigger is not a fill, a stop on the long leg could leave a naked short); the bot's exits, the time-stop and FORCE_FLAT manage it. `tighten_stop` moves a sell-stop trigger up only, to at most LTP − 2 ticks, at most `MAX_MODIFY` times per order (Phase 2), by MODIFY in place; a rejected modify keeps the old order and re-reads the order book; a stop is never cancelled and replaced.
   - **`reduce_only(contract)`** (callers: chase, target, time-stop, scratch, FORCE_FLAT, feed freeze, token, HARD KILL, reconcile, CLI) needs the intent's single EXIT TOKEN (an Intent Log field; one holder at a time): (1) `cancel_entries()`: cancel every working non-reducing order of the contract; (2) a working stop or exit order is MODIFIED in place along EXIT_LADDER; only if a modify is rejected or the modify cap is reached: cancel it and poll order details until it is terminal (`cancelled`, `rejected` or `complete`); **never a replacement exit while the old order may still be live**: `complete` → done; a part q filled → the replacement is LOT − q; not terminal after 2 s → its quantity counts as working; (3) `qty = broker net position − Σ working exit qty`; qty ≤ 0 → send nothing, re-poll; (4) **oversell guard:** after every fill and every 1 s while a reduce runs, a broker net short on any contract not covered by a long of the same intent → buy to cover at once (buy side of EXIT_LADDER) and alarm; (5) **orphan sweep:** after FLAT and every 5 s while FLAT, cancel any working order of a contract whose net is 0.
   - **EXIT_LADDER** (the one name for every flatten): reference = the feed's best opposite quote, else the REST quote, else the positions call's last price marked STALE (then the band doubles and an alarm goes out). Rung k = 0 … `N_RUNG = 6`: limit at bid − k × `STEP_TICKS = 2` ticks for a sell (ask + … for a buy), dwell `max(0.5 s, 2 ÷ exit rate)`, applied by MODIFY of the same order; the last rung sits at the exchange's price-band edge (Phase 2) and is repeated every 1 s, never cancelled without a replacement. Unfilled after the last rung → **EXIT_STUCK**: alarm now and every 60 s; widen to the band the exchange allows; rerun every 10 s on a fresh reference; a lone short not bought within 30 s with the owner's `HEDGE_BUY = ON` (default OFF) buys one protective lot once; at `broker_mis_cutoff − 2 min` journal `AT_RISK_OF_BROKER_SQUAREOFF`. Every wait is cut into 1 s slices that each write the heartbeat.
   - **Chase (SL-limit jump-through).** A broker-side SL-limit is a limit order: a gap can pass its limit and leave it open while the option keeps falling. When the marketable side (bid for a long, ask for a short; LTP only when both are missing) is beyond the stop's trigger for more than 1.5 s and the stop is not filled, or the stop shows triggered (`open`) with the bid below its limit: `reduce_only`, which walks the stop itself down EXIT_LADDER by modify. Fault test F3 proves it.
   - **Daily mark-to-market lock:** every 1 s with a position open, realized loss today + the open position marked at the bid ≥ the daily lock → `reduce_only` and the day is locked before any new signal is read.
   - *Process model (one order path, three processes).* (i) The bot (Python) hosts the gateway in-process. At start it opens `state/gateway.lock` (close-on-exec; never truncated or unlinked before the lock is held), takes `fcntl.flock(LOCK_EX | LOCK_NB)` (held → exit 78 `ALREADY_RUNNING`, no retry), then truncates and writes `{pid, boot_id, start_ticks, role, epoch}` (`start_ticks` = field 22 of `/proc/<pid>/stat`, parsed after the last `)`) and fsyncs; bumps `state/epoch.json` (write a temp file, fsync, rename; a separate file, never the Intent Log); runs BOOT_RECONCILE; only then opens the feed. Every subprocess uses `close_fds=True`. A start-up self-test runs a second process that must FAIL `LOCK_NB` on `state/` (else LIVE_BLOCKED reason LOCKFS). The gateway reads `state/epoch.json` before building an order, immediately before the socket write (no I/O in between) and after the ack: stale before the write → refuse; stale after the ack → journal `LATE_ORDER` and reconcile at once. A process that finds its epoch stale writes `FENCED`, stops its heartbeat and exits 77. (ii) `python3 -m bot.gateway` is the SAME package as a one-shot CLI. `--status` is READ-ONLY: it never bumps the epoch, takes the lock, signals a process or sends an order; it prints the Intent Log tail, the epoch, the lock holder, the heartbeat and the broker's positions and orders. `--reduce-only --reason <r>`: writes `CLI_START`; bumps `state/epoch.json` (a live holder fences itself and exits 77); takes the `flock`: still held by a bot after 2 s → SIGKILL the holder only after its `{boot_id, start_ticks}` and a command line containing `bot` match, wait until `/proc/<pid>` is gone (≤ 5 s), then lock; held by a CLI whose heartbeat `seq` moved in the last 5 s → wait up to 30 s, then act as an observer; then wait 1.5 s (in-flight packets), reconcile from broker truth (the log is read tolerantly; a torn line never stops a flatten), `reduce_only` every leg (short first), write `CLI_DONE {result}`; exit 0 = flat confirmed, 3 = NO_TOKEN, other = failed. `reduce_only` is a safety action and is never blocked by a lock. (iii) The Go watchdog is a separate process with NO broker credentials, NO token path and NO order URLs (a grep test). Heartbeat: the bot's DECISION LOOP (never a helper thread) writes `state/heartbeat.json` `{pid, start_ticks, epoch, seq, order_in_flight}` by temp + fsync + rename at least every `HB_PERIOD_S = 1` s; the watchdog, on ITS OWN monotonic clock, declares a miss when `seq` has not moved for `HB_MISS_S = 6` s (+ `T_HTTP` once while `order_in_flight`; `HB_MISS_S ≥ 2 × T_HTTP`), counts an unreadable file as no change, never acts before the first beat or after `state/clean_exit`. On a miss it SIGTERMs the verified bot PID, SIGKILLs after 2 s, confirms the process is gone (≤ 5 s), then runs the CLI as its child and reads its exit code and `CLI_DONE`: failure → retry every 5 s up to 6 times, then write `state/KILL_FAILED` and run the owner's alert command (B10) every 60 s until he clears it. The watchdog writes `state/watchdog.beat` every 1 s.
B3 **Execution**: entry → confirm the fill → protective stop per B2. Exit by SL / target / time-stop / scratch. Strictly intraday: force-flat at `FORCE_FLAT_IST = min("15:10:00", broker_mis_cutoff − 5 min)`, with `broker_mis_cutoff` from Phase 2 (`constants.toml`; unverified → assume 15:15:00, so the result is 15:10:00), and on any day on which a contract of the open structure expires (instrument master) at `FORCE_FLAT_EXPIRY_IST = "15:05:00"` or earlier by the same min() rule. At FORCE_FLAT, at every lock and HARD KILL, at the entry cut-off and at `T_L1` the first action is `cancel_entries()`: no resting entry survives them. Still not flat 60 s after FORCE_FLAT → the last rung of EXIT_LADDER at once and an alarm. The bot's own exit must never race the broker's auto-square-off (a clash adds a fee), and a long ITM option must never reach expiry (exercise STT on intrinsic value, Class D). ## RULES · risk limits, balance gate, AGREE, verdict tables (loaded at 2c, 3c, 4A, 6, 7)

### K0 Pins
`config/PINS.sha256` holds the SHA-256 of `gates.toml`, `limits.toml`, `config/gateway.toml`, `tools/secret_patterns.txt` and `tools/secret_allow.txt` (a file that does not exist yet enters by a PIN BUMP); `tools/check_pins.py` (≤ 80 lines) exits non-zero on any mismatch and runs in pre-push and CI. A legitimate change is a PIN BUMP: one commit that changes the pinned file plus `PINS.sha256` and nothing else, message `PIN: <file> <reason>`, one line in `results/pin_log.md` (old hash → new hash, direction, reason). The same check compares with the pin at the previous freeze tag (no freeze tag yet: the first PIN BUMP is checked against the K1 chain only and logged `FIRST` in `pin_log.md`; tighten-only applies from the second): `limits.toml` and `config/gateway.toml` may only tighten (MIN up, MAX down, every loss limit down); the floors of `gates.toml` never fall below `archive/gates_v11_floor.toml`. Reviewers compare against the pins and the tag, never the working tree alone.

### K1 `limits.toml` (ONE source of risk limits; pinned, K0)
- Names (keep them and the chain test): CAPITAL_RS, MAX_TOTAL_LOSS_RS, EQUITY_FLOOR_RS, MAX_DRAWDOWN_RS, MAX_TRADE_LOSS_RS, daily / weekly / monthly locks, COOLOFF_MIN, MAX_LOTS, MIN_LIVE_BALANCE_RS, MAX_BALANCE_RS, the boolean LIVE_POSSIBLE; optional OWNER_CEILING_RS, MIN_LONG_OPTION_BALANCE_RS, MAX_TRADE_LOSS_SPREAD_RS. The V10 name `LOSS_FLOOR` stays banned.
- **HARD KILL** = `MAX_TOTAL_LOSS_RS` breached or `EQUITY_FLOOR_RS` touched, whichever comes first.
- **Fixed rupees.** The `_RS` limits are calibrated at `CAPITAL_RS = MIN_LIVE_BALANCE_RS` and stay FIXED in rupees for every `effective_balance` in `[MIN_LIVE_BALANCE_RS, MAX_BALANCE_RS]`: the bot trades 1 lot (`ABS_MAX_LOTS = 1`) whatever the balance, so a larger balance must never linearly scale `MAX_TRADE_LOSS_RS` or any other rupee limit (a larger balance lowers the risk of ruin; it does not buy a bigger bet). `derive_day_limits(effective_balance)` returns the fixed rupee values and moves only `EQUITY_FLOOR_RS = effective_balance − MAX_TOTAL_LOSS_RS`.
- **Windows.** Daily lock = the IST calendar day; weekly = IST Monday to Sunday; monthly = the IST calendar month; `MAX_TOTAL_LOSS_RS` is counted from the first live trade after the last cleared HARD KILL (paper: from the freeze); `COOLOFF_MIN` = minutes after a losing trade, a number written in 3e, ≥ 15.
- **Structure sub-bands.** If the structure selector (LAB L4) uses a debit spread in one balance range and a 1-leg long option in another (boundary `MIN_LONG_OPTION_BALANCE_RS`), `limits.toml` may carry a separate fixed cap `MAX_TRADE_LOSS_SPREAD_RS` alongside `MAX_TRADE_LOSS_RS`, each constant in ₹ across its sub-band and each obeying the chain at the bottom of its sub-band.
- **Chain:** 2 × MAX_TRADE_LOSS_RS ≤ MAX_DRAWDOWN_RS ≤ MAX_TOTAL_LOSS_RS ≤ effective_balance; EQUITY_FLOOR_RS = effective_balance − MAX_TOTAL_LOSS_RS; MIN ≤ MAX whenever LIVE_POSSIBLE.
- **Loss-first sizing (R10; ASSUMPTION defaults, tighten-only: choose tighter with a reason, never looser; per sub-band when there are two).** `MAX_TRADE_LOSS_RS` = the by-construction max loss of the strategy's structure at its strikes (whole structure, 1 lot) plus stressed round-trip charges, rounded up to ₹50, no slack above it. Daily lock = 2 × (the backstop for a loss beyond the by-construction bound, such as a gap or a stuck exit; BOT B2 enforces it on mark-to-market), weekly lock = 4 ×, monthly lock = 8 × `MAX_TRADE_LOSS_RS`, each also ≤ `MAX_TOTAL_LOSS_RS`. `MAX_TOTAL_LOSS_RS` = the smallest value, rounded up to ₹500 and never below 2 × `MAX_TRADE_LOSS_RS`, at which the stressed Monte Carlo gives P(HARD KILL in 12 months) ≤ 5%. `MAX_DRAWDOWN_RS` = the larger of 2 × `MAX_TRADE_LOSS_RS` and half of `MAX_TOTAL_LOSS_RS`. Limits come from the strategy's loss distribution, never from the balance.
- The V11 values (`CAPITAL_RS` ₹15,000 and the ₹4,500-type loss values) are placeholders, not inputs: 3e derives every number again and records the override in one `DECISIONS.md` line.

### K2 Balance ladder and derivation (`docs/BALANCE_LADDER.md`; skeleton in 2c, filled in 3e)
Ladder rows: ₹10k, 15k, 20k, 25k, 30k, 40k, 50k, 75k, 1L, 1.5L, 2L (the balances the owner is likely to hold are rows, so MIN is never rounded up to a far row). Per row and per structure (long option, debit spread): does 1 lot fit (long option: premium × LOT; debit spread: Leg 1 premium × LOT + the stressed margin to sell Leg 2, 2c); by-construction max loss in ₹ and as % of balance; the risk limits that follow from K1; Monte Carlo P(touch HARD KILL in 12 months) and drawdown p95 under stressed costs; fixed monthly cost as % of balance; the FD baseline per month on that balance.
- `MIN_LIVE_BALANCE_RS` = the smallest ladder balance where ALL hold: 1 lot fits; by-construction max loss ≤ the per-trade limit; the chain of K1; P(touch HARD KILL in 12 months) ≤ 5% (stressed); fixed monthly cost ≤ half of the stressed base-case monthly net result PRE-TAX (otherwise live is not worth it at that balance).
- `MAX_BALANCE_RS` is derived on its own, not as a formula of MIN: the largest ladder row R with R ≤ m × MIN (m chosen by you, default 2, justified: only 1 lot was validated, so funds above it stay idle) on which all the MIN conditions still hold (and R ≤ `OWNER_CEILING_RS` when the owner gave one). Both are stored as their own numbers.
- No row up to ₹2L passes, or the smallest passing row is above `OWNER_CEILING_RS` (code MIN_ABOVE_OWNER_CEILING) → `LIVE_POSSIBLE = false` in `limits.toml` and the MIN / MAX keys are omitted (TOML has no null; a string like "none found" never goes into a numeric field). The bot ships paper-only, the verdict carries NO_LIVE_BALANCE_UP_TO_2L (or MIN_ABOVE_OWNER_CEILING), and report point 3 says it plainly.
- All values live in `limits.toml` with their derivation tag. The 3e values are PROVISIONAL (ESTIMATE) until Phase 7 has measured real spreads on DATA-R and DATA-P. Phase 7 may only TIGHTEN: raise MIN, lower MAX, lower a loss limit. If a raised MIN would pass MAX, the result is `LIVE_POSSIBLE = false`, never an inverted band. Loosening anything later needs the owner (he edits `limits.toml` himself and re-pins).

### K3 Gate behavior in code (each case has a test)
- PAPER mode: any virtual balance, no min or max, same strategy, same stressed cost model, journaled.
- LIVE mode: first read `LIVE_POSSIBLE` (false or key absent → LIVE_BLOCKED always); then read usable broker funds at start and before every entry. The funds call fails → LIVE_BLOCKED (fail-safe).
- funds < MIN → no live entry, the bot runs PAPER and logs `LIVE_BLOCKED balance < MIN`. If the balance falls below MIN during the day: no new live entries, an open position keeps its protection (single option: its broker-side stop; debit spread: its by-construction bound). Live resumes only when funds ≥ MIN and the owner re-arms.
- funds > MAX → `effective_balance = MAX`. The rupee loss limits do not grow with the balance; only `EQUITY_FLOOR_RS` follows it, computed at the first start of each day and stored in `state/day_start.json` (B4).
- HARD KILL, in THIS order: (1) write and fsync `state/hard_kill.flag` `{reason, ts, counters}`; (2) `cancel_entries()`; (3) flatten through `reduce_only`; (4) lock every entry. The flag is read at process start, by the CLI (which still flattens), before every entry and by `arm`; only the owner clears it by hand, after reading the journal.
- The chain test holds for every balance in [MIN, MAX], and `MIN ≤ MAX` holds. `MAX_TRADE_LOSS_RS` (and every `_RS` limit but the floor) is the same number at every balance of the band (or across each structure sub-band): a test proves it.

### K4 Loss budget and GO numbers
`LB = 0.5 × MAX_DRAWDOWN_RS` (as in `limits.toml`): the cumulative stressed net ₹ of the paper days, from the freeze, may never fall to −LB, checked after every closed trade and on the mark-to-market of an open position every minute; a breach sets `LB_BREACHED = yes` until the next freeze. `GO_N = 40` trading days AND `GO_M = 60` trades of PAPER, counted only from the latest change of `strategy_hash` or `params_hash` (a Phase 7 strategy, parameter or cost-model change restarts the count; a bug fix does not).

### K5 AGREE (the pass rule behind every "agreement" check between two engines)
A trade-level match = same date, same structure / strike / expiry, same entry bar and exit reason, |Δ net ₹| ≤ max(₹2, 1% of |net|). Agreement = matched / (nA + nB − matched). Pass: on a slice whose union (nA + nB − matched) holds ≥ 100 trades, agreement ≥ 99%; on a smaller slice, at most 1 mismatch and it carries a cause line naming a fill-model difference, never a logic difference (both engines are deterministic code, and 99% of 5 trades is not a measurable thing). A slice with nA = nB = 0 is EMPTY: guard the division; it passes nothing and a longer one is taken. Slices are chosen by trades, not by time: the smallest contiguous run of days holding ≥ 20 trades, or the whole DESIGN window when it holds fewer. Every mismatch is listed in `results/replay_mismatch.csv`. The engine of record wins: the other side is fixed or the candidate is dropped. Results live in `results/replay_agreement.json` under the keys `vec_vs_eor` (3c: lab vs engine of record), `eor_vs_gateway_slice` (4B), `eor_vs_fullbot` (5: feed adapter → strategy → gateway → PaperBroker). The Phase 7 journal-vs-replay thresholds (95% / 80%) are in V2.
